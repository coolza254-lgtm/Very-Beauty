# Very Beauty — Skincare Tracker (Spec สำหรับ Claude Code)

เอกสารนี้คือ spec ตั้งต้นของโปรเจกต์ ให้ Claude Code อ่านก่อนเริ่มทำงานทุกครั้ง
ภาษาเอกสาร: ไทย (ชื่อตัวแปร/โค้ด/คอมเมนต์ในโค้ดใช้ภาษาอังกฤษ) · ภาษา UI เริ่มต้น: ไทย

---

## 1. ภาพรวม

**Very Beauty** คือแอพมือถือ (Android + iOS) สำหรับบันทึกและติดตามสกินแคร์ทุกอย่าง:

- ติดตามสินค้า ราคา ปริมาณ และความคุ้มค่า (บาทต่อกรัม / บาทต่อครั้ง / วันที่คาดว่าจะหมด)
- บันทึกการใช้สินค้าในแต่ละวัน (เช้า/เย็น) ผ่านเช็คลิสต์ที่กดไม่กี่แตะ
- ถ่ายรูปหน้าเพื่อติดตามผลเทียบกันตามเวลา
- บันทึกสภาพผิวรายวันแบบละเอียด (คะแนน, อาการ, ปัจจัยแวดล้อม)
- ชั่งน้ำหนักสินค้าเป็นระยะเพื่อดูว่าใช้ไปเท่าไหร่

## 2. หลักการออกแบบ (สำคัญ ต้องยึดตลอด)

1. **Offline เต็มรูปแบบ**: ทุกฟีเจอร์หลักทำงานได้โดยไม่ต้องมีอินเทอร์เน็ต ไม่มี backend ไม่มีบัญชีผู้ใช้
   - ข้อยกเว้นเดียวที่ใช้เน็ต: **การตรวจสอบเวอร์ชันใหม่ของแอพ** (ดูหัวข้อ 8) ต้องล้มเหลวเงียบๆ ได้เมื่อออฟไลน์
2. **ความเป็นส่วนตัวมาก่อน**: รูปหน้าและข้อมูลทั้งหมดอยู่ในเครื่องเท่านั้น ไม่ส่งออกไปไหน ไม่มี analytics/tracking ของบุคคลที่สาม
3. **ใช้งานเร็ว ลดจำนวนแตะ**: การบันทึกประจำวันต้องจบได้ในไม่กี่วินาที ทุกอย่างที่ละเอียดต้องเป็นตัวเลือก ข้ามได้เสมอ
4. **ละเอียดเมื่ออยากละเอียด**: ฟอร์มสองระดับ — หน้าหลักกรอกแค่ที่จำเป็น ส่วน "รายละเอียดเพิ่มเติม" พับไว้
5. **ไม่ใช้ AI วิเคราะห์ภาพ** ใน MVP (ตัดสินใจแล้วว่าไม่จำเป็น — เทียบผลด้วยความรู้สึกและรูปถ่ายของผู้ใช้เอง) อย่าเพิ่มโมเดล ML ถ้าไม่ได้ขอ
6. **ไม่ใช่เครื่องมือวินิจฉัยทางการแพทย์** ต้องมีข้อความชี้แจงสั้นๆ ในหน้า About/Onboarding

## 3. Tech Stack

- **Framework**: Flutter (stable ล่าสุด), Dart null-safety, รองรับ Android + iOS จากโค้ดชุดเดียว
- **State management**: Riverpod
- **Routing**: go_router
- **Database**: SQLite ผ่าน `drift` (migrations ให้ถูกต้องตั้งแต่เวอร์ชันแรก)
- **รูปภาพ**: เก็บเป็นไฟล์ใน application documents directory (ไม่ลงแกลเลอรีของเครื่อง) เก็บเฉพาะ path ใน DB
- **กล้อง**: `camera`
- **กราฟ**: `fl_chart`
- **แจ้งเตือน**: `flutter_local_notifications` (+ `timezone`) ทำงานแบบ local ทั้งหมด
- **ล็อกแอพ**: `local_auth` (Face ID / ลายนิ้วมือ / PIN ของเครื่อง) ตัวเลือกเปิด/ปิดได้
- **Export/Import**: `archive` (zip), `share_plus`, `file_picker`
- **ข้อมูลแอพ/เวอร์ชัน**: `package_info_plus`, `url_launcher`
- **Android in-app update**: `in_app_update` (ดูหัวข้อ 8)
- **ตัวเลือกภายหลัง**: `mobile_scanner` (สแกนบาร์โค้ด)
- **Localization**: `flutter_localizations` + ARB (เริ่มด้วย th, เตรียมโครงสำหรับ en)
- **Lint/test**: `flutter_lints`, unit test สำหรับสูตรคำนวณ, widget test สำหรับหน้าหลัก

> ถ้าเห็นว่าแพ็กเกจใดล้าสมัยหรือมีทางเลือกที่ดีกว่า ให้แจ้งผู้ใช้พร้อมเหตุผลก่อนเปลี่ยน

## 5. โครงข้อมูล (SQLite / drift)

เวลาเก็บเป็น epoch milliseconds (UTC) ยกเว้น `daily_entries.date` เก็บเป็น `YYYY-MM-DD` ตามเวลาท้องถิ่นของผู้ใช้
ทุกตารางมี `id` (integer PK autoincrement), `created_at`, `updated_at`

> **สถานะ implementation: schema version 3** (`lib/core/db/tables.dart`, snapshot ใน `drift_schemas/`)
> - ตารางเชื่อม `entry_tags` / `product_tags` ใช้ composite primary key (`entry_id, tag_id` / `product_id, tag_id`) แทน `id`
> - ค่า enum เก็บเป็นข้อความ snake_case เช่น `in_use`
> - คะแนน 1–5 (`score_*`, `stress_level`, `rating`) มี CHECK constraint
> - `app_settings.key` และ `daily_entries.date` เป็น unique, `tags` unique ตาม (`name`, `type`)
> - Foreign key เปิดใช้งาน: ลบสินค้า → ลบ weight/usage logs, routine steps, product tags ตาม; ลบ routine → `usage_logs.routine_id` เป็น NULL; ลบ daily entry ที่ยังมีรูปไม่ได้ (restrict)
> - `photos.file_path` / `thumb_path` เก็บเป็น path สัมพัทธ์จาก application documents directory (ย้ายเครื่อง/restore แล้วไม่พัง)
> - ข้อมูลตั้งต้น: tag อาการ/ปัจจัย ภาษาไทย และ routine "เช้า" / "เย็น"
> - **v3**: เพิ่ม `products.barcode` (text?) สำหรับฟีเจอร์สแกนบาร์โค้ด — **ผู้ใช้ให้เอาฟีเจอร์ออกแล้ว** คอลัมน์ยังคงอยู่ (ไม่ได้ใช้) เพื่อไม่ต้อง migrate ฐานข้อมูลของผู้ที่ติดตั้ง build 11 ไปแล้ว
> - **v2**: เพิ่ม `products.finished_date` (int?, epoch ms) — วันที่ปิดสินค้าเป็น "ใช้หมด" ใช้กับเส้นมาร์กในกราฟ Insights

(พอลิเมอร์ สารสกัด น้ำมัน ฯลฯ) และ `popular` (ส่วนผสมเด่นตามประเภทสินค้า)
สร้างจาก `tool/ingredients/` (`python3 tool/ingredients/build.py`, ต้องมี RDKit) — แก้ที่ไฟล์ข้อมูล Python แล้ว build ใหม่ (ไม่ต้อง migrate)

- Seed tag เริ่มต้นเป็นภาษาไทย เช่น symptom: ระคายเคือง, แสบ, ผิวลอก, ผื่น · factor: นอนน้อย, เครียด, ตากแดดนาน, อาหารที่สงสัย · ผู้ใช้เพิ่มเองได้

## 6. สูตรคำนวณ (ต้องเขียน unit test ครบ)

ใส่ไว้ใน `core/utils/calculations.dart` เป็นฟังก์ชันบริสุทธิ์ (pure functions)

- **ใช้ไปแล้ว (g)** = `start_weight − น้ำหนักล่าสุด`
- **เหลือกี่ %**
  - ถ้ามี `empty_bottle_weight`: `(น้ำหนักล่าสุด − empty) ÷ (start_weight − empty) × 100`
  - ถ้าไม่มี: ประมาณจาก `net_content` โดยสมมติความหนาแน่น ≈ 1 g/ml → `(net_content − ใช้ไปแล้ว) ÷ net_content × 100` และแสดงเครื่องหมาย "ประมาณ"
- **อัตราใช้ต่อวัน (g/วัน)** = `ใช้ไปแล้ว ÷ จำนวนวันตั้งแต่ opened_date` (หรือตั้งแต่ weight log แรก)
- **วันที่คาดว่าจะหมด** = วันนี้ + `ปริมาณคงเหลือ ÷ อัตราใช้ต่อวัน` (ถ้าข้อมูลน้อยเกินไป ให้แสดงว่า "ยังประมาณไม่ได้")
  - _implementation_: นับจาก **วันที่ชั่งล่าสุด** แทน "วันนี้" เพราะปริมาณคงเหลือวัดได้ ณ วันนั้น (ถ้านับจากวันนี้จะนับเวลาที่ผ่านไปซ้ำ) และอัตราใช้ต่อวันคิดถึงวันที่ชั่งล่าสุดเช่นกัน
- **บาทต่อกรัมที่ใช้จริง** = `price ÷ net_content` (ราคาต่อหน่วยตามฉลาก) และ **ต้นทุนที่ใช้ไปแล้ว** = `price × (ใช้ไปแล้ว ÷ net_content)`
- **บาทต่อครั้ง (โดยประมาณ)** = `ต้นทุนที่ใช้ไปแล้ว ÷ จำนวน usage_logs ของสินค้านั้น`
- **คะแนนผิวเฉลี่ยช่วงที่ใช้สินค้า** = เฉลี่ย `score_*` ของ `daily_entries` ในวันที่มี usage_logs ของสินค้านั้น
- Edge cases ที่ต้องรองรับ: ไม่มีราคา, ไม่มีน้ำหนัก, ชั่งเพียงครั้งเดียว, น้ำหนักล่าสุดมากกว่าเริ่มต้น (ชั่งผิด → เตือนผู้ใช้), หน่วย ml

## 7. หน้าจอและฟีเจอร์

### 7.1 Today (หน้าแรก)
- เช็คลิสต์ routine เช้า/เย็น: แตะติ๊กว่าใช้ตัวไหนแล้ว → สร้าง usage_logs
- ปุ่ม "ใช้ตามปกติ" ติ๊กทั้งชุดในครั้งเดียว
- ปุ่มลัดถ่ายรูป และปุ่ม "บันทึกสภาพผิววันนี้"
- แจ้งสินค้าที่ใกล้หมด/ใกล้หมดอายุ/ถึงเวลาชั่ง (ถ้ามี)

### 7.2 Products
- รายการ (กรองตาม status/category), ค้นหา
- ฟอร์มเพิ่ม/แก้ไข แบบสองระดับ (จำเป็น: ชื่อ, ประเภท, ราคา, ปริมาณ · พับ: รายละเอียดอื่น)
- หน้ารายละเอียด: แถบ "เหลือประมาณ xx%", กราฟน้ำหนักตามเวลา, บาทต่อครั้ง, วันที่คาดว่าจะหมด, คะแนนผิวเฉลี่ยช่วงที่ใช้
- ปุ่ม **"ชั่งใหม่"**: ช่องตัวเลขใหญ่ คีย์บอร์ดตัวเลขเด้งอัตโนมัติ แสดงส่วนต่างจากครั้งก่อนทันที
- ปิดสินค้า (finished) พร้อมให้คะแนนและเลือกซื้อซ้ำ/ไม่ซื้อซ้ำ
- Wishlist: เก็บสินค้าที่อยากซื้อ เทียบ "บาทต่อกรัม" กับของที่ใช้อยู่

### 7.3 Routines
- สร้าง/แก้ชุดเช้า/เย็น จัดลำดับขั้นตอนด้วยการลาก
- ตั้งเวลาแจ้งเตือนต่อชุด

### 7.4 Daily skin log
- ให้คะแนน 1–5 หลายด้าน (ใช้ slider/chips แตะเร็ว)
- แท็กอาการและปัจจัยแวดล้อมแบบเลือกเร็ว
- โน้ตอิสระ
- ทุกช่องเป็นตัวเลือก บันทึกได้แม้กรอกบางส่วน

### 7.5 Photos
- กล้องพร้อม **กรอบไกด์วงรี** และ **ภาพของครั้งก่อนจางๆ ซ้อนอยู่** (onion skin) เพื่อจัดตำแหน่งเดิม
- เตือนเรื่องแสง (ข้อความแนะนำ เช่น ถ่ายใกล้หน้าต่าง แสงเดิมทุกครั้ง) — ไม่ต้องวิเคราะห์ภาพ
- บันทึกรูปเต็ม + thumbnail แยกกัน
- ลบข้อมูล EXIF/ตำแหน่งที่ตั้งออกจากรูปที่บันทึก
- แกลเลอรี/Timeline และหน้า **เทียบรูปสองใบ** (เลือกสองวัน ลากสไลด์เทียบ)

### 7.6 Insights
- ปฏิทิน: แต่ละวันมีจุดสี/รูปย่อ แตะดูสรุปของวันนั้น
- กราฟคะแนนผิวตามเวลา พร้อมเส้นมาร์กวัน "เริ่มใช้สินค้าใหม่" / "ใช้หมด"
- ค้นหา/กรอง เช่น "วันที่ผิวระคายเคือง" แล้วดูว่าใช้อะไรไปบ้างในช่วงก่อนหน้า
- สรุปค่าใช้จ่าย/ความคุ้มค่า ต่อเดือน และต่อสินค้า

### 7.7 Settings
- แจ้งเตือน (ชุดเช้า/เย็น, ชั่งน้ำหนักทุก 1–2 สัปดาห์, PAO) เปิด/ปิดได้
- ล็อกแอพ (local_auth)
- ธีม (สว่าง/มืด/ตามระบบ), ภาษา
- **Backup / Restore** (หัวข้อ 9)
- ตรวจสอบอัปเดต + เวอร์ชันปัจจุบัน
- About: ข้อความชี้แจงว่าไม่ใช่เครื่องมือวินิจฉัย, นโยบายความเป็นส่วนตัวสั้นๆ

## 8. การอัปเดตแอพจากในแอพ (In-app update)

**เป้าหมาย**: เมื่อมีเวอร์ชันใหม่ แอพแจ้งผู้ใช้และพาอัปเดตได้จากในแอพ
**ข้อจำกัดของแพลตฟอร์มที่ต้องออกแบบตาม** (ให้ Claude Code ตรวจสอบเอกสารปัจจุบันของ Apple/Google ก่อนลงมือ เพราะนโยบายเปลี่ยนได้):

### Android
- **ช่องทางหลัก (แนะนำ)**: Google Play In-App Updates API ผ่านแพ็กเกจ `in_app_update`
  - Flexible update (ดาวน์โหลดเบื้องหลัง แล้วถามให้รีสตาร์ท) เป็นค่าเริ่มต้น
  - Immediate update เฉพาะกรณีอัปเดตสำคัญ/จำเป็น
  - ต้องติดตั้งจาก Google Play (รวม internal/closed testing track) จึงจะทำงาน
- **ถ้าแจกจ่ายนอก Play** (เช่น ไฟล์ APK เอง): ทำได้โดยเช็ค `version.json` จากโฮสต์ที่ผู้ใช้กำหนด → ดาวน์โหลด APK → เรียกตัวติดตั้งของระบบ (ต้องขอสิทธิ์ `REQUEST_INSTALL_PACKAGES` และผู้ใช้ต้องอนุญาตเอง; ใช้ไม่ได้กับบิลด์ที่ขึ้น Play Store) ให้ทำเป็น build flavor แยก

### iOS
- **iOS ไม่อนุญาตให้แอพดาวน์โหลดและติดตั้งตัวเองได้** ต้องอัปเดตผ่าน App Store/TestFlight เท่านั้น
- สิ่งที่ทำได้: เช็คเวอร์ชันล่าสุด (เช่น iTunes Lookup API ด้วย bundle id) เทียบกับเวอร์ชันปัจจุบัน → แสดง dialog "มีเวอร์ชันใหม่" พร้อมปุ่มเปิดหน้า App Store ด้วย `url_launcher`

### ตัวเลือกเสริม (ตัดสินใจภายหลัง)
- **Shorebird (code push สำหรับ Flutter)** ส่งแพตช์โค้ด Dart ถึงผู้ใช้ทั้งสองแพลตฟอร์มโดยไม่ต้องผ่านรีวิวสโตร์ แต่ไม่ครอบคลุมการเปลี่ยนโค้ดเนทีฟ/ปลั๊กอินใหม่ และมีเงื่อนไขการใช้งาน ให้ประเมินก่อนใช้จริง

> **สถานะ implementation (Phase 6)** — ตอนนี้แจกจ่ายเป็นไฟล์ APK ผ่าน GitHub Releases จึงใช้ทางนี้ก่อน:
> - `GitHubReleasesUpdateService` อ่าน release ล่าสุด (`build-N`) จาก GitHub API เทียบกับ build number ของแอพ → แสดง dialog → เปิดลิงก์ดาวน์โหลด APK ในเบราว์เซอร์ (ไม่ต้องขอสิทธิ์ `REQUEST_INSTALL_PACKAGES`; ผู้ใช้แตะไฟล์เพื่อติดตั้งเอง)
> - `min_supported_build: N` ในคำอธิบาย release = บังคับอัปเดต
> - `AppStoreUpdateService` (iOS) ใช้ iTunes Lookup API ไว้แล้ว รอขึ้น App Store
> - Google Play In-App Updates (`in_app_update`) ยังไม่ได้เพิ่ม เพราะใช้ได้เฉพาะแอพที่ติดตั้งจาก Play — เพิ่มเป็น implementation ใหม่ของ `AppUpdateService` เมื่อขึ้น Play
> - ตรวจตอนเปิดแอพไม่เกินวันละครั้ง ปิดได้ใน Settings, ปุ่ม "ตรวจสอบอัปเดต", ล้มเหลวเงียบๆ เมื่อออฟไลน์

### การออกแบบในโค้ด (`core/update/`)
- abstraction `AppUpdateService` เดียว มี implementation แยกตามแพลตฟอร์ม/ช่องทาง
- ตรวจเวอร์ชันตอนเปิดแอพ (ไม่เกินวันละครั้ง) และมีปุ่ม "ตรวจสอบอัปเดต" ใน Settings
- ทุกอย่างล้มเหลวเงียบๆ เมื่อออฟไลน์ ห้ามบล็อกการใช้งานแอพ
- มี `min_supported_version` ได้ (เผื่อบังคับอัปเดตเมื่อมีการเปลี่ยน schema ที่เข้ากันไม่ได้ — ใช้อย่างระมัดระวัง)
- เป็นการเชื่อมต่ออินเทอร์เน็ตเพียงอย่างเดียวของแอพ ต้องระบุในนโยบายความเป็นส่วนตัวและไม่ส่งข้อมูลผู้ใช้ไปด้วย

## 9. Backup / Restore (สำคัญมากเมื่อเป็นออฟไลน์)

เปลี่ยนเครื่องหรือเครื่องเสียแล้วข้อมูลจะหายหมดถ้าไม่มีสำรอง
- **Export**: สร้างไฟล์ `.zip` = ไฟล์ฐานข้อมูล (หรือ JSON export) + โฟลเดอร์รูปทั้งหมด + `manifest.json` (เวอร์ชันแอพ, schema version, วันที่สร้าง) แล้วส่งออกผ่านหน้าแชร์ของระบบ (เก็บลง Files/Drive/AirDrop ได้ตามที่ผู้ใช้เลือก)
- **Import**: เลือกไฟล์ zip → ตรวจ manifest → แจ้งก่อนว่าจะแทนที่ข้อมูลปัจจุบัน → restore
- รองรับการ migrate เมื่อ schema version ต่างกัน
- เตือนให้สำรองข้อมูลเป็นระยะ (เช่นทุกเดือน, ปิดได้)
- มี unit/integration test สำหรับ export แล้ว import แล้วข้อมูลต้องตรงเดิม

- ผู้ใช้ไม่ได้เป็นนักพัฒนา Flutter มาก่อน อธิบายขั้นตอนที่ต้องทำเองให้ชัด (ติดตั้ง Flutter, ตั้งค่า Xcode/Android Studio, เซ็นแอพ, อัปโหลดขึ้น store) ภาษาง่าย
- ทุกครั้งที่แก้ schema ให้เขียน migration และอัปเดตเอกสารนี้ในหัวข้อ 5
- รักษาหลักการในหัวข้อ 2 (offline, privacy, ใช้งานเร็ว) เหนือสิ่งอื่น
